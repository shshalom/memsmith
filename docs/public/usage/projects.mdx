# Projects

MemSmith keeps memory per project. A project is identified by a non-secret marker file, `.memsmith/project.json`, that holds the project id and team id. The credential for the team lives in `~/.memsmith`, never in the marker.

## How a folder finds its project

When a session starts, MemSmith looks for a marker in this order. The nearest marker always wins, so a repository or folder with its own marker keeps its own project.

1. **The folder's own repository.** MemSmith checks the session folder and each parent up to the git root. Outside git, it checks only the session folder at this step.
2. **The main checkout of a worktree.** If the folder is in a linked git worktree that has no marker, MemSmith uses the project of the main checkout, before it looks anywhere above the worktree.
3. **Above the repository, only where you allow it.**
   - **Inside a search root.** If the folder is inside a folder listed in `MEMSMITH_PROJECT_SEARCH_ROOTS`, MemSmith checks each parent above the git root, up to and including the search root. It never looks above the search root. When search roots overlap, the innermost one applies.
   - **Outside git and outside every search root.** MemSmith checks each parent up to your home folder, but never a marker directly in your home folder, because that marker would claim every project on the machine.
   - **Everywhere else**, including a repository outside every search root, nothing above the git root counts. A search root affects only the folders inside it. For example, `/tmp/scratch` never uses a marker in `/tmp`.

If MemSmith finds no marker, the project root is the git root, or the session folder outside git. A new project, in a team of its own, is created there.

MemSmith compares folders after it resolves symbolic links, and it ignores letter case on macOS and Windows.

### Git worktrees

MemSmith reads the worktree's `.git` file and the repository's git directory to find the main checkout, and doesn't run `git`. The main checkout is the folder whose `.git` folder is the repository's git directory, or the folder that `core.worktree` names in the repository's git config. When the main checkout has no project yet, MemSmith creates the project at the main checkout, so every worktree of a repository shares it. If neither rule names the main checkout, for example in a repository created with `git init --separate-git-dir` and no `core.worktree`, the worktree keeps its own project. A submodule is always its own project.

## Notices

When a session creates a project, its context includes a line such as the following. If the project is created on your first prompt instead, that prompt's context carries the line.

```
MemSmith created project api for /Users/ana/Workspace/api. Run `memsmith project` to check it, or `memsmith link` to use a different project.
```

When a session uses a project whose marker is above its own folder, such as a search-root marker or a worktree's main checkout, its context includes a line such as the following, once for each folder:

```
MemSmith is using project Workspace from /Users/ana/Workspace for this folder. Run `memsmith project` to check it, or `memsmith link --new` to give this folder its own project.
```

## Check a folder's project

To see which project a folder uses, run `memsmith project` in it:

```
Folder:        /Users/ana/Workspace/api/src
Project root:  /Users/ana/Workspace
Project:       Workspace (7f3c9a2e-1b4d-4e8f-9c6a-2d5e8b1f0a37)
Team:          4b1e6d90-8a3f-4c2e-b7d5-91f0e3a6c812 (local)
Runtime:       local
Resolved by:   marker in ~/Workspace (search root ~/Workspace)
Search roots:  ~/Workspace
```

The project name comes from the running server. When the server isn't running, MemSmith shows the folder name instead. If MemSmith ignored an entry in `MEMSMITH_PROJECT_SEARCH_ROOTS`, `memsmith project` says which one and why. `memsmith status` also prints a `Project:` line for the current folder.

## Pin a folder to a project

`memsmith link` writes a marker at the folder's git root, or in the folder itself outside git. Inside git, it also adds `.memsmith/*` to `.git/info/exclude`, once. It doesn't change `.gitignore`. If `.git/info/exclude` already excludes the `.memsmith` folder itself, MemSmith changes that line to `.memsmith/*`, because git can't re-include a file inside an excluded folder, and a later Go Team convert re-includes `.memsmith/project.json`.

| Command | Result |
| --- | --- |
| `memsmith link` | Pins the project that the folder resolves to now. If the folder resolves to no project, MemSmith creates one. |
| `memsmith link <project-id>` | Pins the project with that id. The server must be running. |
| `memsmith link <project-name>` | Pins the project with that name. The server must be running. If more than one project has the name, MemSmith lists their ids and changes nothing. |
| `memsmith link <path>` | Pins the project that another folder uses. A path must contain `/` or start with `.` or `~`; any other argument is read as a project id or name. |
| `memsmith link --new` | Creates a fresh project, even when a folder above has a project. |

If the folder already has a marker for a different project or team server, `memsmith link` shows the change and stops. To replace the marker, add `--force`. MemSmith never replaces a team project's marker with a local one, even with `--force`, and it never links your home folder itself. To link to a team project, pass the path of a folder that already uses it.

After it writes the marker, `memsmith link` registers the project with the local server so search works right away. If the server isn't reachable, the next session in the folder registers it.

## List your projects

To see every project that the local server knows, run `memsmith projects`. For each project, it shows the name and id, the team (`local`, or a joined team and its server), the runtime, the folders that link to it, its database, its record counts (observations, notes, and events), and its last activity. Add `--json` for output that scripts can read.

A project's folders are the folder recorded the last time a session registered it, the current folder's project root, any nested folder whose marker names the project, and any folder up to three levels inside a search root whose marker names it. A recorded folder whose marker now names another project isn't listed.

`memsmith projects` marks a project with these flags:

| Flag | Meaning |
| --- | --- |
| `empty` | MemSmith counted the project's records, and it has no observations, notes, or events. A project whose records MemSmith couldn't count is never marked `empty`. |
| `missing-db` | The project has no database yet, usually because no session in it has written anything. |
| `orphan-db` | A project database exists, but no project names it, and no marker names it as a project's database. |
| `stray` | A marker in a subfolder of another project's root names this project. Usually a session that started in the subfolder created it. |
| `merging` | A merge started but didn't finish. Search leaves the project out until you run the merge again. |
| `archived` | `memsmith merge` folded this project into another one. |

`memsmith projects`, `memsmith merge`, and `memsmith projects --prune` work with the local runtime only, and they read the embedded Postgres directly. If it isn't running, start it with `memsmith start`.

## Merge one project into another

To fold one local project's records into another, run `memsmith merge <from> <into>`. Each project can be a project id, a project name, or a folder path that contains `/` or starts with `.` or `~`.

Without `--yes`, `memsmith merge` changes nothing. It shows how many sessions, events, generation jobs, observations and notes, observation sources, and job history rows it would copy, which rows the target already has, which rows get a new id, which folders it would link to the target, and the exact command to run. To merge, run that command, which ends in `--yes`.

`memsmith merge` refuses, and changes nothing, in these cases:

- The two projects are the same project.
- Either project is a team project, or a project merged into the source earlier has a team marker.
- The target was merged, or is being merged, into a third project.
- The source was merged, or is being merged, into a different project.
- Either project has no database.
- The two projects keep their records in the same database.
- The server hasn't recorded which database holds your projects, for example after `memsmith stop`. Run `memsmith start` first.
- Another merge or prune is running.

Otherwise, with `--yes`, `memsmith merge` does the following:

1. Backs up the source project's database with `pg_dump` to `~/.memsmith/backups/merge-<project-id>-<time>.sql`, readable only by you. If the backup fails, the merge stops before it changes anything.
1. Marks the source project as merging, so search, recall, and the dashboard project list leave it out from then on.
1. Copies the source project's sessions, events, generation jobs, observations, notes, embeddings, observation sources, and job history into the target project, in one transaction. Queued and running generation jobs are copied as queued. Rows keep their ids and their exact timestamps. A row the target already has, such as a session that ran in both folders, isn't copied again, and the copied rows point to the target's row. A row whose id the target uses for a different row gets a new id that ends in `-m` and the first eight characters of the source project id. Failed and cancelled generation jobs stay with the source.
1. After the copy commits, cancels the source's queued and running jobs, which are now queued in the target. The running server picks up those jobs only when it starts, so when the merge moved any, it asks you to run `memsmith restart`. If the copy fails, it's rolled back, the source's jobs stay as they were, and the source is no longer marked as merging.
1. Marks the source project archived. Its database stays.
1. Links every folder that MemSmith knows uses the source project, or a project merged into the source earlier, to the target project. MemSmith never changes a team project's marker.
1. Copies any rows that the source project received, or that changed, during the merge.

If a step fails, `memsmith merge` says which steps finished and what the target holds. Every step can run again, so to finish a merge that stopped, run the same command again. It copies only rows that the target doesn't have yet, and updates sessions and observations that changed in the source since the last copy.

Search, recall, and the dashboard show the merged records right away, because they read the target project's database, and the embeddings are copied with the records.

A folder that still links to the archived project keeps working. The server routes its captures, searches, and dashboard reads to the project it was merged into, following a chain of up to eight merges, and refuses the request when the merges form a cycle. The next time a session starts in that folder, MemSmith rewrites the folder's marker to name the target project, unless the marker belongs to a team project.

## Prune projects

To see which projects and databases MemSmith can remove, run `memsmith projects --prune`. To remove them, add `--yes`. MemSmith removes these:

- **An orphan database** that holds no records.
- **An empty project**, or a project without a database. MemSmith deletes the project record and, when no other project uses its team, the team and the team's key in `~/.memsmith`.
- **The database of a project archived by `memsmith merge`.** MemSmith keeps the project record, so a folder that still names the project reaches the project it was merged into.

Before it removes anything, MemSmith counts every row in every table of the database, for every project, and keeps the database unless the only rows are the project's own team and project records, or, for an archived project, rows no newer than the merge. MemSmith keeps a project, and says why, in each of these cases:

- It couldn't count the project's records, or every table in its database.
- The database holds account rows, such as keys, members, or another team's records, or holds rows of another project.
- Another project, or a marker, names the same database, or the project keeps its records in a shared database.
- A folder still links to it, no folder is recorded for it, or the scan of a search root stopped early.
- It's a team project, or a merge into it is still marked as in progress.
- An archived project's database has rows newer than the merge. Run the merge again to copy them, then prune.

`memsmith projects --prune` refuses to run when the server hasn't recorded which database holds your projects, for example after `memsmith stop`. Run `memsmith start` first.

Before it drops a database, MemSmith backs it up with `pg_dump` to `~/.memsmith/backups/prune-<database>-<time>.sql`. Before it deletes a project record, it writes the project, team, member, and key rows it deletes to `~/.memsmith/backups/prune-<project-id>-account-<time>.sql`. Both files are readable only by you, and MemSmith flushes them to disk before it continues. If a backup fails, MemSmith keeps that database and project. Right before each drop, MemSmith counts the database again, and keeps it if it changed. After it drops a database, it asks you to run `memsmith restart`, so the server releases its connections to the dropped database.

## Restore from a backup

The backups are plain SQL. To restore one, use the tools in `~/.memsmith/pg-binaries/bin` against the embedded Postgres, which listens on port 55433 unless you set `MEMSMITH_LOCAL_PG_PORT`.

1. Start MemSmith, which starts the embedded Postgres:

   ```bash
   memsmith start
   ```

1. Set up the tools and the connection. On Linux, use `LD_LIBRARY_PATH` instead of `DYLD_LIBRARY_PATH`.

   ```bash
   export PGBIN=~/.memsmith/pg-binaries/bin
   export DYLD_LIBRARY_PATH=~/.memsmith/pg-binaries/lib
   export PGURL=postgres://memsmith:memsmith-local@127.0.0.1:55433
   ```

1. To restore a dropped project database, create it and load its backup. The database name is in the backup file name.

   ```bash
   "$PGBIN/createdb" --dbname="$PGURL/postgres" msp_<id>
   "$PGBIN/psql" "$PGURL/msp_<id>" -v ON_ERROR_STOP=1 -f ~/.memsmith/backups/prune-msp_<id>-<time>.sql
   ```

1. To restore a deleted project record, load its account backup into the database that holds your projects. `memsmith projects --json` prints its name as `accountDatabase`; on most installs it's `postgres`. Use that name in place of `postgres` in this step and the next.

   ```bash
   "$PGBIN/psql" "$PGURL/postgres" -v ON_ERROR_STOP=1 -f ~/.memsmith/backups/prune-<project-id>-account-<time>.sql
   ```

1. To undo a merge, make the source project active again, so search and the dashboard read it:

   ```bash
   "$PGBIN/psql" "$PGURL/postgres" -c "UPDATE projects SET metadata = metadata - 'mergedInto' - 'mergingInto' - 'archivedAt' WHERE id = '<source-project-id>'"
   ```

   If you also pruned the source's database, restore it first with step 3, from the `merge-<source-project-id>-<time>.sql` backup or the later `prune-` backup. Then link the source's folders to it again with `memsmith link <source-project-id> --force` in each folder.

1. The rows a merge copied stay in the target. To remove them, delete the target's rows whose ids appear in the source database, in this order. Rows renamed during the merge have ids that end in `-m` and the first eight characters of the source project id.

   ```sql
   -- In the target database, for each table: observation_generation_job_events,
   -- observation_sources, observations, observation_generation_jobs, agent_events,
   -- server_sessions. List the source ids from the restored source database first.
   DELETE FROM observations WHERE project_id = '<target-project-id>' AND id = ANY('{<source ids>}');
   ```

   Rows the target already had, such as a session that ran in both folders, weren't copied, so their ids aren't in the source database under the target's id. Back up the target with `pg_dump` before you delete anything.

1. Run `memsmith restart`.

## Find stray markers

A session that starts in a subfolder before the project root has a marker can create a separate project for that subfolder. `memsmith doctor` looks for these. For each project root that the local server knows, and for the current folder's project root, it checks subfolders up to three levels down, and skips `node_modules`, build folders, and hidden folders. For each subfolder marker that names a different project, it shows the nested project's record count and the command that folds it in:

```
memsmith merge <nested-project-id> <root-project-id>
```

The merge links the nested folder to the root project. A nested folder that is its own git repository is a project of its own, and `memsmith doctor` doesn't report it. `memsmith doctor` never changes markers or records, even with `--fix`. When it can't reach the embedded Postgres within two seconds, it checks only the current folder's project root.

## Converting a shared marker

Go Team convert refuses a project whose marker is above the git repositories that use it, because converting it would move every one of those repositories to the team. To convert one repository, run `memsmith link --new` in it, and then convert that project. Convert checks only git repositories up to three folder levels below the marker, using the search roots in your settings file at the time of the convert. It doesn't check folders outside git that use the marker.
