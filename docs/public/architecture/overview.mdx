# Architecture overview

## System components

MemSmith runs as a Claude Code plugin with these components:

1. **Plugin hooks**: A Setup version check plus lifecycle hooks that capture prompts and tool use, inject context, and enforce memory-first lookups.
2. **MemSmith server**: One server engine that stores observations, generates them with the configured provider, and serves search, context, and the viewer.
3. **Storage**: Postgres with pgvector for full-text and semantic search. The local runtime runs an embedded Postgres; the team runtime connects to a remote one.
4. **MCP server**: Exposes memory tools (`observation_search`, `observation_get`, `observation_context`, `note_add`, and others) and the `smart_*` code exploration tools.
5. **Viewer UI**: A React dashboard served by the MemSmith server.

## Runtimes

| Runtime | Storage | Use |
|---------|---------|-----|
| `local` (default) | Embedded Postgres in `~/.memsmith/pgdata`, port `55433` | A single user on one machine. No Docker. |
| `server` | A remote Postgres reached through the team's MemSmith server | Shared team memory. |

The server listens on `127.0.0.1`. Its default port is derived from your user ID (`38877 + uid % 100`) so that accounts on a shared machine don't collide.

## Data flow

### Capture

```
Hook (stdin) → MemSmith server (/v1/events) → generation job → Postgres
```

1. Claude Code sends prompt and tool data to a hook on stdin.
2. The hook posts the event to the MemSmith server.
3. The server queues a generation job, and the configured provider turns the event into an observation.
4. The server stores the observation and its embedding in Postgres.

### Recall

```
SessionStart hook or MCP tool → MemSmith server (/v1/search, /v1/context) → Postgres → Claude
```

At session start, the context hook injects recent and relevant observations. During a session, Claude calls `observation_search` for a ranked index and `observation_get` for full records through the MCP server.

## Plugin hooks

`plugin/hooks/hooks.json` registers these hooks. Each lifecycle hook runs `bun-runner.js`, which starts `server-service.cjs` with a `hook claude-code <event>` argument:

| Event | Matcher | Handler |
|-------|---------|---------|
| Setup | `*` | `version-check.js` (marker check; never installs anything) |
| SessionStart | `startup\|clear\|compact` | Starts the server, then `context` (context injection) |
| UserPromptSubmit | | `session-init`, `prompt-injection`, `record-intent` |
| PreToolUse | `Read` | `file-context` |
| PreToolUse | `Grep\|Glob\|WebSearch` | `discovery-gate` |
| PreToolUse | `mcp__plugin_memsmith_mem__.*` and `Grep\|Glob\|Read\|Bash` | `tool-intent` |
| PreToolUse | `Task\|Agent` | `agent-directive` |
| PreToolUse | `mcp__plugin_memsmith_mem__observation_add` | `record-intent-intercept` |
| PostToolUse | `*` | `observation` |
| Stop | | `answer-gate` (memory-first answer check, then `summarize`) |

`npx memsmith install` and `npx memsmith repair` install the runtime dependencies. The Setup hook only reads the `.install-version` marker.

For details, see [Plugin Hooks](/architecture/hooks).

## Memory-first answering

Session-start context and the memory that MemSmith injects into the context have different jobs:

- **Orientation.** The `context` hook injects the latest observations at session start, under the label "Latest context for orientation". This context tells Claude what happened recently. It isn't the source for answers.
- **Answering.** When a prompt asks about past work, decisions, rationale, history, configuration, the status of earlier work, or what a teammate did, the answer comes from a memory search.

The hooks enforce this in three steps:

1. **`UserPromptSubmit`.** The `prompt-injection` hook looks for a clear retrieval signal in the prompt: a question about decisions, rationale, history, how something was done, where something is configured, or the status of earlier work. For such a prompt, it injects a directive: search memory with `observation_search`, then `observation_get` for the relevant ids, answer from the results, say so plainly when memory has no record, then validate load-bearing claims against the code. It records the turn as a pending information request. Every other prompt gets nothing and costs no memory search; memory-first for those is the agent's own step, backed by the standing directive and the `tool-intent` gate.
2. **`PreToolUse`.** A call to `observation_search`, `observation_get`, or `observation_context` satisfies the pending request. The `tool-intent` hook also marks the question's topic as consulted, so the discovery gate doesn't block the follow-up code search on the same subject. `session_start_context` doesn't count, because it returns orientation context. The `smart_*` code tools and the memory write tools don't count either.
3. **`Stop`.** In `hard` mode, if the turn's information request is still unsatisfied, the `answer-gate` hook returns a block decision with the reason "Search memory (observation_search) before answering". Claude Code then continues the turn so Claude can search. The gate blocks at most once per turn, and never when `stop_hook_active` is set, in `soft` mode, for a subagent, or when memory is unavailable. `summarize` runs after the gate, on the `Stop` that ends the turn.

Prompts that refer to the current conversation, such as "you just said", "above", "earlier in this chat", or "the plan you wrote", are exempt: what was already said needs no search.

Outside those prompts, the standing directive, given at session start and to every subagent, asks the agent to follow one flow whenever it needs information: do I already know this from this conversation? If not, search memory. Then validate against the code. The `tool-intent` hook enforces the middle step at the moment the agent reaches out: before the first Grep, Glob, search-style Bash command, or web search on a topic, `hard` mode blocks the call until the agent has consulted memory for that topic with `observation_search` or `observation_context`, and `soft` mode adds a reminder. A web fetch isn't gated, because it acts on a URL already in hand. The gate runs no memory search of its own and injects no memories. When the memory server can't be reached, the gate allows the call and adds a notice that memory is unavailable. These hooks run in Claude Code; Codex gets the session-start directive only.

To stop enforcing memory-first behavior, run `npx memsmith enforcement off`. The command writes `settings.json` directly, so it works while hard mode is blocking. To see the mode that the hooks use and whether it comes from the default, `settings.json`, or the environment, run `npx memsmith enforcement status`.

Codex keeps its existing hooks. Its `PreToolUse` hook doesn't run for MemSmith's memory tools, so a Codex turn could never be marked as searched.

## Directory structure

```
memsmith/
├── src/
│   ├── cli/handlers/           # Hook event handlers
│   ├── server/                 # MemSmith server: routes, runtime, generation, retrieval
│   ├── servers/mcp-server.ts   # MCP server
│   ├── storage/postgres/       # Postgres schema and queries
│   ├── npx-cli/                # `npx memsmith` commands
│   ├── services/               # Integrations, telemetry, transcripts, shared services
│   ├── ui/viewer/              # React viewer
│   └── shared/                 # Paths, settings defaults, shared utilities
├── scripts/                    # Build and maintenance scripts
├── plugin/                     # Plugin distribution
│   ├── .claude-plugin/plugin.json
│   ├── hooks/hooks.json
│   ├── scripts/                # Built bundles: server-service.cjs, mcp-server.cjs, bun-runner.js, version-check.js
│   ├── skills/                 # ms-mem-search, ms-smart-explore, ms-how-it-works, ms-dashboard
│   └── ui/                     # Viewer bundle
├── tests/                      # Test suite (`bun test`)
└── docs/public/                # Documentation source
```
