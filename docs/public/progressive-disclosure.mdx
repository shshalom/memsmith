# Progressive disclosure

MemSmith gives the agent a small amount of context at session start and a set of tools to fetch more. The agent decides what to read, in order from cheapest to most expensive. This design keeps the context window free for the task and keeps each memory lookup proportional to what the agent needs.

## The layers

| Layer | Source | What the agent gets |
|-------|--------|---------------------|
| 1. Orientation | `SessionStart` hook | The standing directives and the most recent observations of the project. |
| 2. Index | `observation_search` | A ranked list: id, date, type, actor, title, and a snippet of about 200 characters. It returns 10 results by default and at most 25. |
| 3. Records | `observation_get` | The full record for up to 10 ids: body, why, files, and rejected alternatives. |
| 4. Code structure | `smart_outline`, `smart_search` | Symbols and signatures with the bodies folded. |
| 5. Code | `smart_unfold`, then `Read` | The source of one symbol, then the whole file. |

`observation_context` combines layers 2 and 3 for the case where the agent doesn't need to choose. It returns the full bodies of the top matches (5 by default, at most 10), capped at about 20,000 characters.

## Layer 1: orientation at session start

The `context` hook injects the latest observations under the label "Latest context for orientation". The number comes from `MEMSMITH_CONTEXT_SESSION_COUNT` (default `10`, clamped to 1 through 50). This context tells the agent what happened recently. It isn't the source for answers.

The hook also injects the memory-first directive, which tells the agent to follow this order whenever it needs information:

1. Check whether the conversation already contains the answer.
2. If not, search memory with `observation_search`, then fetch the relevant records with `observation_get`.
3. Validate load-bearing claims against the current code.

## Layers 2 and 3: search, then fetch

`observation_search` returns an index so that a broad query stays small. A search that returned every matching record in full could exceed the tool output limit of Claude Code. After the agent picks the records that matter, `observation_get` returns them in full.

```
observation_search(query="hook timeout", limit=10)
observation_get(ids=["<id>", "<id>"])
```

## Layers 4 and 5: code

When memory points to a file, the agent reads as little of it as it needs:

```
smart_outline(file_path="src/cli/hook-command.ts")
smart_unfold(file_path="src/cli/hook-command.ts", symbol_name="hookCommand")
```

The `Read` tool is the last step. The hook on `Read`, `file-context`, injects nothing at present. For token measurements of the code tools, see [Smart Explore benchmark](/smart-explore-benchmark).

## How the hooks keep the order

The hooks make the order the default without injecting memories into each prompt:

- `prompt-injection` detects a question about past work and tells the agent to search memory before it answers.
- `tool-intent` asks the agent to consult memory before its first `Grep`, `Glob`, search-style `Bash` command, or `WebSearch` on a topic.
- In `hard` enforcement mode, both checks block once, and the agent continues after it searches memory. In `soft` mode, they remind.

For details, see [Architecture overview](/architecture/overview#memory-first-answering).

## Design choices

- **Show cost before content.** An index of titles and snippets costs far less than the records it points to.
- **Let the agent choose.** The agent knows the task, so it decides which index entries deserve a full read.
- **Treat memory as a pointer.** A record can be stale. The agent validates it against the code before relying on it.

For the general principles behind this design, see [Context engineering](/context-engineering).
